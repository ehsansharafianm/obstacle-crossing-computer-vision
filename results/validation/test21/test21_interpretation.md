## Interpretation

### 1. Precision — excellent
Each distance stays constant to **±2–6 mm (std)** as the rigid wand moves through the
volume — about **1–2 % of the length**. The system is highly repeatable: a fixed
distance reconstructs to nearly the same value everywhere in the space. This is the
`distance_vs_time` plot — the solid lines are flat.

### 2. Accuracy — a systematic ~5–6 % underestimate
Every pair reads **shorter than the truth**, by a **proportional** amount
(~5–7 % on all six, mean ratio ≈ **0.94**). In the `measured_vs_known` plot the points
sit on a straight best-fit line of slope ≈ **0.94**, *below* the ideal `y = x`.

**Proportional error = a SCALE error**, not random noise (that would scatter both ways)
and not a fixed offset (that would be a constant mm on every pair, not a constant %).
The whole reconstruction is uniformly ~6 % too small.

### 3. Most likely cause
A pure scale error traces to the **physical size the calibration was told the board is**.
The pipeline used **62.9 mm** squares for the large board
(`results/calibration/active/board_measured_large.json`). If the real squares are
~**66–67 mm**, that alone gives 62.9 / 66.6 ≈ **0.944** — matching the observed scale.
Because scale propagates, **every** result (obstacle heights, foot heights, clearances)
computed under calib17 is ~5–6 % low in absolute terms.

## Recommended fix
1. **Measure several calibration-board squares with calipers**, average them.
2. If they differ from 62.9 mm, update `board_measured_large.json` and re-run
   `build_calibration 17` (cameras unmoved). This removes the bias at the source.
3. **Re-verify the wand marker center-to-center spacings**, so the reference itself is exact.
4. **Interim:** multiply reconstructed distances/heights by ≈ **1.06** to correct scale.

## Takeaway
The camera system is **precise** (sub-2 % repeatability) and, once the scale is
corrected, will also be **accurate**. This is exactly why a wand check matters — the
precision numbers alone would never have revealed the scale bias.
